# VerifyMaster 智能体架构报告

## 概述

`VerifyMaster` 是一个面向 BrowseComp 数据集的三智能体工作流，核心思想是：

**先搜索，再验证，最后提交答案。**

系统将任务拆分为三个角色：

- **Planner**：决定下一步该调查什么，或者判断当前证据是否已经足够回答问题
- **Executor**：使用网页工具为某个聚焦子任务收集证据
- **Verifier**：审查收集到的证据，并判断它是否足够可靠

整体目标是在避免过早作答的同时，尽量减少无效的反复搜索。

---

## 三个智能体的角色

### 1. Planner Agent

Planner 是整个流程的调度者。

主要职责：

- 阅读原始 BrowseComp 问题
- 查看当前研究轨迹
- 决定下一步应执行的聚焦子任务
- 判断何时可以停止研究并输出最终答案

输出格式：

- `<task>...</task>`：继续研究，给出一个明确的下一步子任务
- `<answer>...</answer>`：直接给出最终答案

Planner **不直接使用网页工具**。

---

### 2. Executor Agent

Executor 是证据收集者。

主要职责：

- 接收 Planner 分配的单个子任务
- 在网页上搜索与该子任务直接相关的证据
- 抓取候选网页并提取关键事实
- 输出简洁的证据报告，并附带来源链接

可用工具：

- `think`
- `finish`
- `google_search`
- `web_fetch`

设计原则：

- Executor 每次只解决 **一个缺失线索**
- 不应试图一步完成整道题，而应逐步补全关键证据

---

### 3. Verifier Agent

Verifier 是质量控制者。

主要职责：

- 审查 Executor 提交的每一步证据
- 审查最终候选答案
- 判断当前支持是否足够强
- 当证据不足时给出简短、可执行的反馈

当前工具策略：

- 只保留 `think`
- 不直接进行网页搜索或网页抓取

判断风格：

- 整体上更偏“谨慎但不过度苛刻”
- 重点关注 **答案本身是否被充分支持**
- 不要求所有背景线索都逐条独立闭环，只要剩余不确定性不会实质影响最终答案即可

---

## 工作流的不同阶段

### 阶段 1：任务初始化

一次运行开始时，系统会：

- 加载一条 BrowseComp 问题
- 创建三个智能体
- 注册自定义浏览工具
- 将 Executor 的 `web_fetch` 工具绑定到它自己的 LLM
- 初始化一条空的研究轨迹

---

### 阶段 2：规划阶段

每一步中，Planner 会接收到：

- 原始问题
- 当前步骤编号
- 之前研究步骤的摘要
- 之前验证阶段给出的反馈

Planner 必须做出二选一决策：

- 提出下一个子任务
- 或者输出最终答案

这个阶段负责保证整体搜索方向保持聚焦，避免无目标地反复搜索。

---

### 阶段 3：执行阶段

如果 Planner 输出的是子任务，那么 Executor 会执行面向该子任务的网页研究。

典型行为如下：

1. 先识别当前缺失的关键线索
2. 使用 `google_search` 寻找有希望的来源
3. 使用 `web_fetch` 抽取相关事实
4. 输出一份简洁的证据报告

证据报告通常应包含：

- 具体事实
- 与当前子任务的直接对应关系
- 来源 URL 或来源名称

---

### 阶段 4：局部验证阶段

Executor 返回证据之后，Verifier 会执行 **局部验证（local verification）**。

局部验证主要检查：

- 证据是否与当前子任务相关
- 证据是否具体，而不是泛泛而谈
- 证据是否足够推动问题继续收敛
- 是否存在明显的无依据猜测

可能结果：

- **PASS**：该步骤被接受，并写入研究轨迹
- **FAIL**：系统要求 Executor 换一个角度重试一次

这一阶段的作用是避免低质量搜索结果污染后续推理。

---

### 阶段 5：弱证据重试阶段

如果局部验证失败：

- Verifier 的反馈会被附加到下一次 Executor 指令中
- Executor 会被要求调整搜索词、来源类型或验证角度
- 系统会在限制次数内重试该子任务

这个重试机制是轻量的，目标是纠偏，而不是把整道题从头做一遍。

---

### 阶段 6：最终答案提议阶段

当 Planner 认为当前证据链已经足够时，它会输出：

```xml
<answer>...</answer>
```

这里的答案必须尽量短、尽量精确，并符合 BrowseComp 对答案粒度的要求。

---

### 阶段 7：全局验证阶段

在最终答案真正被接受之前，Verifier 会执行 **全局验证（global verification）**。

全局验证主要检查：

- 候选答案是否被研究轨迹直接支持
- 被识别出的实体是否已经相对明确
- 是否还存在强竞争候选
- 最终答案是否仍然依赖猜测

当前的判断标准是：

- 只要答案本身被强支持，即使部分背景线索只做到部分验证，也可以通过
- 只有当缺失证据真的可能改变最终答案时，才应判定失败

如果全局验证通过：

- 任务直接结束，输出最终答案

如果全局验证失败：

- 失败反馈会被写入研究轨迹
- Planner 会基于这些反馈继续安排后续补证任务

---

### 阶段 8：最终兜底阶段

如果达到最大步骤数后仍未完成全局验证：

- 系统会让 Planner 基于当前轨迹再做一次最终综合
- 输出当前最有支持度的答案
- 运行状态记为 `max_steps`

这个兜底逻辑可以保证系统即使没有完全完成验证，也不会无结果退出。

---

## Research Trajectory 的作用

该架构中的核心状态对象是 **研究轨迹（research trajectory）**。

每一个被记录的步骤都会保存：

- 步骤编号
- 子任务描述
- 证据内容
- 验证结果
- 重试次数

研究轨迹有两个主要作用：

- 给 Planner 提供跨步骤的结构化记忆
- 给 Verifier 提供一条可审查的证据链

因此，这个系统不是简单的多轮对话，而是一个围绕“显式证据状态”循环推进的工作流。

---

## 为什么采用这种架构

和单智能体浏览式求解相比，这种设计将三个问题拆开处理：

- **策略制定** -> Planner
- **证据收集** -> Executor
- **证据审查** -> Verifier

优势：

- 减少过早输出最终答案
- 让失败原因更容易分析
- 让 Planner 能根据验证反馈动态调整方向
- 将网页浏览能力集中在一个智能体上，职责更清晰

代价：

- 整体流程通常比单智能体更慢
- 如果 Verifier 过严，可能会阻塞正确答案
- 如果 Verifier 过松，则可能过早接受低质量证据

因此，当前实现采用的是一种 **中等偏宽松的 verifier 策略**：

- 对“答案是否有支撑”保持严格
- 但不要求每个背景线索都达到同样强度的闭环验证

---

## 当前实现的简要总结

在当前版本的 `VerifyMaster` 中：

- **Planner** 负责控制搜索方向
- **Executor** 是唯一的浏览型智能体
- **Verifier** 只基于已有轨迹审查证据质量和最终答案支持度
- 整个系统按照 **plan -> execute -> local verify -> retry if needed -> final answer -> global verify** 的循环推进

因此，`VerifyMaster` 本质上是一个面向 BrowseComp 的、以验证为中心的多智能体求解框架，而不只是一个单纯的网页搜索 agent。
